# 教学模式与案例

按当前困难选读。下列例子用于说明教学方式，不要求其他项目使用相同语言、框架、状态名或参数。

## 1. 函数对象、调用与调用栈

适用问题：“这里只定义了函数，它在哪里执行？”“这一行传的是返回值吗？”

对照当前代码展示：
- 注册或传递函数对象的位置。
- 实际调用的位置；如果由框架触发，补充路由、回调或调度入口。
- 输入、返回值及调用者恢复执行的位置。

~~~python
def number():
    return 7

action = number       # 函数对象
value = number()      # 整数 7
result = action()     # 调用此前保存的函数
~~~

用户困惑在嵌套调用时，画出活动调用栈，逐次标出参数绑定与返回；不要只重复“这是匿名函数”。

## 2. 并发、回调与响应顺序

适用问题：“收到接受响应就完成了吗？”“为什么旧请求反而后返回？”

在源码中找出提交工作与等待结果的位置。线程池、协程、事件和定时器应按实际实现解释；提交与完成不可混同。

对过期响应防覆盖，用两个请求 A、B 的时间线展示：
- 共享计数器递增。
- 每次请求捕获的局部 generation。
- 响应回来时的比较。
- 过期响应被忽略后，哪些页面值保持当前选择。

区分网络请求是否发出、服务端是否完成，以及客户端最终是否采用响应。

## 3. 类型、容器与数据变换

适用问题：“参数里到底是什么？”“为什么返回的是列表而不是数字？”

一次列出输入类型、具体样例、变换操作和输出类型，避免同名变量遮蔽数据层次。

~~~text
证据列表：
[{path: "a.py"}, {path: "a.py"}, {path: "b.py"}]

列表长度 → 3 个片段
提取路径并去重，再计数 → 2 个文件
~~~

用户看不懂推导式时，先写等价循环，再解释简写。JSON 解析时分别标出外层响应对象、内部字符串和再次解析后的对象。

## 4. 状态、事件与持久化

适用问题：“日志显示完成，但数据库还是运行中。”“函数里赋值了，数据库为什么没变？”

把以下层次按项目实际名称分开：
- 内存中的局部值或字典。
- 工作流内部状态。
- 已提交的数据库记录。
- 进度事件与结束通知。
- 前端最后一次获取的数据。

沿写入顺序定位观察窗口。已提交事务不会因随后另一段代码异常而自动回滚；单个事务内部的异常才按其边界处理。

若某种停止原因只是转入报告，不要仅凭名称将其等同于整个任务失败。执行成功、结论有证据和实际修复通过也分别判断。

## 5. 构建与历史数据

适用问题：“保存页面代码后刷新为什么没变化？”“新增字段为何显示占位符？”

先确认运行模式：直接源码执行、开发服务器、生产构建或长期运行的进程。解释当前程序读的是源码、启动配置还是构建产物，不统一要求“全部重启”。

新字段同时检查生产、保存、接口返回、客户端类型和显示。旧记录可能没有字段；在 JavaScript 中，数字 0 的缺失兜底可使用 ?? 保留零值，具体实现仍由目标语言决定。

修改展示不自动重算历史记录。展示迁移、结果重算或补写应作为不同任务说明。

## 6. 测试与质量评估

适用问题：“Mock 通过算真实服务联调了吗？”“Hit@k 是解决率吗？”

从被测能力往回解释：
- 行为测试验证特定约定；断言应能发现错误实现。
- 检索候选命中、解释质量、修改正确和修复验证是不同目标。
- 附样本来源、分母、去重与排名规则、配置、计时范围和验证日期。
- 模拟响应不证明真实服务质量；展示 Token 不自动构成费用或性能实验。
- 开发集用于选择方案；观察测试集后继续调参会影响独立结论，需要说明或新增留出数据。

具体项目的题数、维度、候选预算和成绩都重新读取当前证据，不把先前案例的数值作为其他项目默认值。

## 7. 用一个完整案例检查理解

用户愿意时，选择一个有可观察输出的小场景：

- 让用户指出入口、参与模块、关键数据类型和最终保存位置。
- 修改任务限定一个行为，给出能区分正确与错误的验收场景。
- 复盘时分别记录用户独立完成、提示后完成、助手完成和仅讲解的部分。

若用户说“直接告诉我怎么做，我只学习”，提供准确位置、完整最小实现和执行链解释，并停止要求其提交作业；不将这个选择记成独立实现通过。
